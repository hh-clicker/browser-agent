# HH Clicker Browser Agent

Инструкция для coding agents: [AGENTS.md](AGENTS.md).

## Помощник на страницах тестов

В управляемом Chrome на `https://assessment.hh.ru/tests/*` Browser Agent внедряет кнопку `ASK CODEX`.
Она читает видимый вопрос и radio-варианты, передаёт их Node-части через Playwright binding и показывает
ответ Generation Agent. Выбранный вариант только подсвечивается — помощник не нажимает radio и не
отправляет форму. Binding принимает запрос только из основной вкладки нужного origin, после реального
клика пользователя и по одному за раз. Токен, CORS-доступ и прямой HTTP-вызов со страницы не используются.

На практических страницах `https://assessment.hh.ru/code/*` появляется такая же кнопка. Помощник
читает видимые условие и счётчик задачи, язык и текущее содержимое Monaco, затем показывает полный
вариант решения с подсветкой синтаксиса в панели слева. Помощник не копирует код в буфер и не изменяет
редактор. При переходе к другой задаче готовое решение сбрасывается. Вставка, запуск кода и отправка
решения всегда остаются за пользователем.

Generation Agent должен поддерживать `POST /questions` и `POST /code-solutions` и быть доступен по
`HH_CLICKER_GENERATION_URL` (по умолчанию `http://127.0.0.1:17374`). Один клик создаёт ровно одно
задание, затем Browser Agent только опрашивает его состояние. Повторный ручной клик создаёт новое
задание, что позволяет повторить неудачную генерацию. Для аварийной диагностики оба помощника можно
отключить переменной `HH_CLICKER_ASSESSMENT_ASSISTANT_ENABLED=false`; пользовательского переключателя нет.

## AI-сопроводительные письма

### Статус генератора

В AI-настройках резюме и диалоге запуска отображается статус Generation Agent, модель, reasoning, версия CLI, очередь
и снимок лимитов. Backend передаёт в heartbeat идентификатор требуемой проверки. Browser Agent обращается к
`GET /health` и `GET /auth/status` один раз для нового идентификатора; повторные heartbeat только доставляют локальный
снимок. Кнопка «Обновить» вызывает `POST /api/v1/generation-agent/status/refresh`, backend меняет идентификатор, а
Browser Agent вызывает `POST /auth/status/refresh`. Одновременные клики объединяются, повторная проверка допускается
после 30 секунд, если предыдущий ответ потерян.

Проверка не требует открытого Chrome и не запускает генерацию. Статус старше 60 секунд помечается устаревшим; при
отключённом Browser Agent готовность не утверждается. «Готов» подтверждает доступный сервис и действующую авторизацию
на момент `checkedAt`; лимиты остаются снимком, а доступность выбранной модели проверяется только реальной генерацией.

### Настройка писем

В настройках резюме и в диалоге запуска есть отдельные AI-шаблон и обычное (резервное) письмо. AI выключен по умолчанию.
Шаблон содержит ровно один `#AI_CHANGE#`. Модель генерирует середину; агент вставляет её буквально, сохраняя шапку и подвал.
Лимит 200–5000 символов относится к готовому AI-письму, минимум 200 оставляется для середины.

Перед запуском обновите backend (миграция 016), frontend, Browser Agent и образ `generation-agent`.
Сервис генерации запускается отдельным Compose-проектом, авторизация остаётся в его существующем volume.
Browser Agent обращается к нему с хоста по `http://127.0.0.1:17374`. При другом порте задайте переменную окружения перед запуском агента:

```powershell
$env:HH_CLICKER_GENERATION_URL = 'http://127.0.0.1:17374'
```

Порядок: открыть деталку → прочитать описание и проверить существующий отклик → запросить середину → собрать и сохранить письмо на backend → получить разрешение → нажать «Откликнуться».
Уже отправленные отклики не запускают генерацию. Настройки и текст резюме фиксируются при создании запуска; описание берётся из текущей деталки.
Тексты резюме и вакансии передаются в локальный `generation-agent`, а оттуда в Codex для генерации.

На попытку допускается один POST с Idempotency-Key, далее только polling; автоматического повторного POST нет.
Ожидание генерации ограничено 210 секундами. При непустом резервном письме обычные ошибки генерации используют его
автоматически. `RATE_LIMIT` всегда ставит запуск на отдельную паузу: пользователь может повторить генерацию либо явно
разрешить резерв для оставшейся очереди. При пустом резервном письме fallback запрещён; ошибка AI становится задачей
внимания без отправки отклика. Общая ошибка конфигурации/авторизации может остановить очередь, локальная или временная
ошибка позволяет перейти к следующей вакансии, но три технических сбоя подряд ставят запуск на паузу.
Пауза/отмена проверяются во время ожидания и до отправки: полученный позднее текст не даёт разрешения на отклик. Уже начатая генерация в сервисе может завершиться самостоятельно.

Готовый текст или безопасный результат ошибки, источник, ID генерации и техническая причина сохраняются до решения
backend о дальнейшем действии.
В «Откликах» раскройте «Подготовленные письма по вакансиям». Подготовка письма сама по себе не подтверждает его отправку.
Для первой живой проверки используйте одну выбранную вакансию. Генерация и отклик не запускаются при сохранении настроек.

Локальный процесс, который управляет браузером через Playwright и обменивается командами с backend HH Clicker.

Browser Agent запускается непосредственно на компьютере пользователя. Он не входит в Docker Compose: это позволяет открывать видимый браузер на хосте и хранить его профиль рядом с локальным приложением.

## Назначение процесса

Агент ожидает команды backend, открывает системный Google Chrome с постоянным локальным профилем, проверяет вход в HH, читает резюме и выдачу, выполняет подтверждённые пользователем запуски откликов. Heartbeat передаёт состояние агента и генератора; результаты команд сохраняются на backend.

## Проверка входа в HH

После `OPEN_BROWSER` и по команде `CHECK_AUTHORIZATION` агент открывает `https://hh.ru/applicant/profile/me`. Для повторных проверок используется та же вкладка, пока пользователь не закрыл её или не перешёл в ней на другую страницу.

- `AUTHORIZED`: профиль успешно загружен на `/applicant/profile/me` в HTTPS-домене HH, без редиректа на вход и без обнаруженной капчи. Имя, кнопки редактирования и наличие резюме для проверки входа не требуются. Список резюме читается отдельно; принадлежность выбранного резюме проверяется перед соответствующим действием.
- `REQUIRED`: HH перенаправил на страницу входа.
- `UNKNOWN`: проверка ещё не выполнялась, страница не загрузилась, появилась капча или разметка не распознана.

Вход и капчу пользователь проходит вручную, затем нажимает «Проверить вход». Постоянного фонового отслеживания входа/выхода нет: интерфейс показывает последний результат проверки. В backend передаются только статус и короткое пояснение — без HTML, cookies, контактов и токенов. Резюме при проверке не импортируются.

На загрузку страницы отведено 15 секунд. Если открылась промежуточная страница HH, на ожидание перехода к профилю, входу или капче отведено ещё до 10 секунд; успешно загруженный профиль не ждёт появления элементов интерфейса. Backend даёт командам запуска и проверки не менее 60 секунд с момента получения агентом. После обновления протокола нужно перезапустить и backend, и агент.

## Явное открытие ссылок и проблемных вкладок

`OPEN_URL` сначала открывает постоянный профиль из payload, если он закрыт, затем
создаёт фоновую вкладку ссылки. Для такого перехода проверка страницы профиля HH
не выполняется. Переключение профилей блокируется backend во время занятых операций.

`FOCUS_VACANCY` — исключение из фонового поведения: по явному клику пользователя
агент вызывает `bringToFront` для сохранённой проблемной вкладки. Предпочтительна
вкладка исходной попытки, иначе выбирается существующая деталка/форма с тем же ID.
Сохранённую вкладку, перенаправленную на вход или капчу HH, также можно показать.
Нет подходящей вкладки — возвращается короткая ошибка, новая вкладка не открывается.
Переходов, reload, кликов и отправки формы эта команда не делает. Команды последовательны:
если выполняется шаг отклика, переключение ждёт его завершения. Фоновая работа агента
сама по себе не вызывает `bringToFront`.

## Панель диагностики селекторов

### Исправление чтения с помощью ИИ

При FAIL у поддерживаемого элемента отчёт содержит `repairableGroups`, а вкладка сохраняется
с непрозрачным `tabId`. По кнопке «Исправить … с помощью ИИ» выполняется отдельная команда
CURRENT с `repairGroup`. Она доступна только свободному агенту, после явного нажатия;
автоматического вызова модели и продолжения откликов нет. Ошибки распознавания поиска и импорта
резюме, а также ошибки запусков дают контекст для этой панели. Панель открыта на `/browser`.

Ошибки рабочих команд могут содержать `selectorDiagnostics`: только подтверждённые FAIL
на загруженной странице, без автоматического вызова ИИ. Контекст включает тип страницы,
проверки и непрозрачный tabId. Капча, вход, отказ в доступе, HTTP-ошибка и мешающий советующий
диалог не превращаются в поломку селекторов. Неопределённый исход отклика сам по себе
не является основанием для починки. Диагностика не меняет исход отправки и не повторяет её.
Проблемные вкладки холостой загрузки и импорта резюме сохраняются для точечной проверки.

В поиске отсутствие дополнительных полей не останавливает сбор. Предупреждение формируется
консервативно: при наличии независимых текстовых признаков зарплаты, опыта, удалённой работы
или меток выплат, которые соответствующий селектор не прочитал. Для ссылки работодателя
дополнительный признак — ссылка `/employer/...` внутри карточки; для местоположения — адрес
из согласованного по ID встроенного JSON, который также виден в тексте карточки.
Это подозрение, не доказательство
новой верстки; отсутствие поля во всех карточках без таких признаков предупреждения не создаёт.
Та же проверка действует в диагностике, чтобы возможную поломку можно было проверить и исправить.
При пагинации сохраняется первая страница с подозрением, дальнейший сбор продолжается в новой
фоновой вкладке. Для одного сканирования сохраняется не более одной такой страницы.

Поддержаны `profile`, `search`, `resumeText`, а в `vacancy` — заголовок, описание и признаки архива.
Селекторы кнопок, форм, подтверждения доставки и их областей действий не восстанавливаются.
При входе, капче, отказе HH в доступе или видимом диалоге исправление не предлагается.
На архивной странице исправляются только заголовок и признаки архива: описание не извлекается,
селекторы отклика не изменяются. Страницы с отказом в доступе или сообщением об удалении
пропускаются диагностикой без ложных поломок селекторов.

Browser Agent строит полный очищенный HTML-снимок в renderer без отсечения по длине,
глубине DOM, количеству узлов или длине полезных атрибутов. Все карточки выдачи и
пагинация сохраняются; тексты и полезные атрибуты передаются,
включая исходную форму href (абсолютную или относительную), ID и обычные параметры ссылок.
Удаляются скрипты, стили, медиа и обработчики; технические секреты в атрибутах/параметрах,
значения скрытых полей и паролей скрываются. Это не обезличивание: снимок может содержать
тексты резюме, вакансий и обычных полей. В Generation Agent передаются снимок,
прежние селекторы чтения, штатные контракты и диагностика каждого ключа (статус, кратность,
видимость, обязательность, причина). `brokenKeys` содержит только явные FAIL и не заменяет
полный отчёт: после восстановления родителя модель должна проверить всех потомков по scope,
включая NOT_CHECKED/NOT_APPLICABLE. Модель опирается на актуальный HTML;
при перестройке DOM разрешена замена связанных областей поиска с проверкой всех прежних PASS.
В backend DOM и ответ модели не передаются. Логи не содержат снимок или ответ.
Generation Agent сохраняет HTML во временный файл задания и даёт модели только чтение
диапазонов и поиск строки в этом файле через отдельный MCP. В текстовый prompt полный HTML
не вставляется. Инструменты чтения универсальны и не привязаны к вёрстке HH.

Кандидат проверяется без записи файла: количество/видимость, требования полей, устранение
исходных FAIL, отсутствие регрессий у прежних PASS и реальное повторное чтение данных.
URL и документ должны оставаться прежними; вход, капча, доступ и диалоги проверяются повторно.
Перед атомарным сохранением сверяется актуальный контекст группы, чтобы не затереть параллельную
правку. Изменяются только локальные replacements; штатные JSON, контракты и другие группы
сохраняются. Ошибка/таймаут модели или неуспешная проверка не меняет локальные селекторы.

BrowserManager хранит последний полный диагностический снимок и его параметры в памяти
текущего браузерного профиля. Починка сохранённой вкладки обновляет соответствующий шаг,
сохраняя остальные результаты и их handles. После восстановления PROFILE проверяется
заблокированный RESUME; после SEARCH — заблокированный VACANCY. Ссылку для зависимого шага
агент читает из исправленной страницы; остальные уже выполненные сценарии не открывает снова.
Новая полная диагностика или закрытие браузера сбрасывает снимок. Результаты других шагов
остаются прежними снимками, а не считаются заново проверенными.

На `/browser` доступны выбор открытой вкладки и полная диагностика.

- **Выбрать вкладку** (`CURRENT` без `tabId`): возвращает `SELECT_TAB` и список `tabs`
  с непрозрачными UUID, типами страниц и номерами вакансий. Заголовки, query-параметры,
  HTML и значения полей не передаются. Список содержит не более 200 открытых страниц.
  После выбора повторный `CURRENT` с `diagnosticTarget.tabId` проверяет именно этот объект
  Page без навигации, reload и переключения фокуса. Тип сценария определяется по URL.
  Закрытые, чужие и устаревшие handles отвергаются; обновление списка заменяет handles.
  Эмуляция Playwright не меняется, события фокуса не отслеживаются и не логируются.
- **Полная диагностика** (`FULL`): последовательно создаёт фоновые временные вкладки
  профиля, печатного резюме, первой страницы сохранённого поиска и вакансии из его выдачи.
  Выбранное локальное резюме сверяется со списком HH. Backend выбирает первый сохранённый
  поиск этого резюме по дате создания/ID; название показано в отчёте. Если резюме не выбрано,
  берётся первое локальное резюме аккаунта по ID; если локальных нет, используется первое
  резюме из профиля HH, а шаг поиска будет пропущен. Ссылки читаются, кнопки карточек не нажимаются.
  Отсутствие поиска, пустая выдача, вход/капча и зависимость от неудавшегося шага объясняются
  отдельно. Пропущенный шаг не выдаётся за поломку селекторов следующей страницы.

Полная диагностика не сохраняет найденные вакансии, тексты или результаты в бизнес-данные,
не запускает обычное сканирование и не получает разрешений отправки. После успешной проверки
временная вкладка закрывается; при проблеме остаётся, отчёт содержит непрозрачный `tabId`.

Рабочие сценарии поиска, печатного резюме, вакансии и обеих форм используют тот же реестр,
что и диагностика. Один запуск операции загружает снимок штатных/локальных селекторов;
внутренние наблюдения, reload и отправка продолжают использовать этот снимок.
Проверки URL, vacancy ID, hash резюме, topicId и разрешения отправки остаются кодом.
CSS и XPath поддерживаются также при чтении полей карточки поиска внутри браузера.

Перед диагностикой поиска применяется то же ожидание стабильных карточек и пагинации,
что и при сканировании. Изменение выдачи во время проверки отменяет снимок без ложных
ошибок отдельных селекторов. Ссылка работодателя необязательна; название компании обязательно.
Шаг, которому помешала ошибка предыдущего шага, получает `BLOCKED`, итог `FAILED` и
описание зависимости. Пустая выдача, отсутствие сохранённого поиска, вход и капча остаются
отдельными причинами неполной проверки, а не поломкой селекторов.
Команда `FOCUS_DIAGNOSTIC` показывает только такую сохранённую вкладку по явному нажатию.
Перезапуск браузера делает старые идентификаторы недействительными. Исходные вкладки не закрываются.

Конкурирующие команды и выполняющиеся отклики блокируют диагностику. На паузе она доступна
для того же профиля после окончания текущего шага. Assessment исключён. Формы отклика и письма
автоматически не открываются: их можно проверить в текущей вкладке после ручного открытия.
Кнопка открытия письма проверяется независимо от открытой формы. Отдельные признаки формы
позволяют отличать её отсутствие от поломки основного селектора; полностью неизвестную форму
без узнаваемых признаков инструмент не способен уверенно распознать.

JSON-контракты содержат `required`, область `scope` (ссылка на элемент либо `{anyOf: [...]}`)
и правила `reads`: `textContent`, `innerText`, `visibleText`, `href`, `closestLinkHref`, `value`,
`nonEmptyValue`, `data-qa-title`, `templateJson`. Зарплатная строка имеет отдельный селектор
`salarySpan`. Кратность дочерних полей проверяется в каждой карточке. Поддерживаются скрытые
служебные значения topicId и JSON в template; их содержимое не возвращается.

Результаты строк: `PASS`, `FAIL`, `NOT_CHECKED`, `NOT_APPLICABLE`. Последний означает закрытую
форму, отсутствующее необязательное поле или неподходящее состояние вакансии. `NOT_CHECKED`
означает настоящую неполноту проверки, включая неизвестное правило или исчерпание бюджета.
Итог `PASSED`/`FAILED`/`INCOMPLETE` учитывает все сценарии: любая поломка приоритетнее пропусков.
Это проверка структуры и читаемых полей, не смысла текста, успешности нажатий или отправки.
Диагностика читает реестр; сценарии с селекторами непосредственно в коде ей не покрываются.

Отчёт содержит CSS/XPath, источник (штатный/локальный), счётчики и причины; полный режим
добавляет четыре `scenarios`. Полный HTML, cookies, контакты, тексты резюме/вакансий и значения
форм не возвращаются. Имя выбранного сохранённого поиска — метаданные контекста отчёта.
Отчёт копируется в JSON и хранится только в ограниченной эфемерной истории команд backend.

## Настройка аккаунта и импорт резюме

Штатные селекторы списка резюме находятся в `resources/hh-selectors/profile.json`.
Имена операций и URL остаются в коде; конфигурация задаёт CSS/XPath и назначение элементов.
У группы есть контекст страницы и задача чтения. У элемента — область поиска, ожидаемая
кратность, тип действия, читаемые поля, признаки подходящего результата и исключения.
`referenceTag` — короткий обезличенный пример прежнего элемента, а не сохранённый HTML
страницы. Он служит подсказкой при восстановлении; по нему нельзя судить о текущем DOM.
Эти описания не выполняют проверки сами по себе: проверки URL, идентичности резюме и
разрешения отправки остаются в сценариях. При подготовке контекста восстановления реестр
берёт текущий селектор, но назначение и ограничения — только из штатной конфигурации.
Локальное исправление не может подменить эти инструкции. Хеш группы учитывает и её
описание, чтобы исправление не пережило изменение требований к элементу.
В том же каталоге подготовлены группы поиска, вакансии, форм отклика и письма, текста
резюме и общих признаков капчи. Пока к реестру подключены чтение списка резюме и
извлечение описания вакансии;
наличие остальных JSON ещё не означает переключение соответствующих сценариев.
Реестр поддерживает отдельный файл `hh-selector-overrides.json` рядом с каталогом профилей
Browser Agent. Чтение использует локальное исправление только при совпадении хеша содержимого
соответствующей штатной группы. Изменение других групп или версии приложения само по себе
не сбрасывает исправление. Устаревшие группы игнорируются и удаляются из сохраняемого набора
при следующей явной записи; повреждённый файл не перезаписывается автоматически.
Штатные JSON-файлы при сохранении исправления не меняются.

После создания локального аккаунта интерфейс переводит на страницу «Браузер» и создаёт его постоянный профиль. Пользователь открывает Chrome, входит в HH вручную и нажимает «Я вошёл — найти резюме».

Команда `DISCOVER_RESUMES` сначала проверяет вход, затем читает карточки в разделе «Мои резюме». В результат попадают только `hhResumeId` (hash из ссылки `/resume/...`, не числовой `data-qa-id`) и название. Служебные шаблоны, cookies и контакты не читаются. Если разметка не распознана, возвращается ошибка, а не успешный пустой список.

После выбора frontend сначала запрашивает профессиональный текст каждого отмеченного резюме через `/api/v1/browser/resume-text`, затем отправляет всю пачку в `/api/v1/resumes/import`. Ошибка чтения одного текста не оставляет частично импортированную пачку. Повторное добавление того же hash в тот же аккаунт не меняет существующие данные и настройки. Hash, связанный с другим локальным аккаунтом, вызывает ошибку; весь пакет откатывается. Новые записи получают локальные настройки откликов по умолчанию. Хранятся hash, название, связь с аккаунтом, plain text и время его загрузки. Автоматической синхронизации с HH и ручного добавления по ссылке нет. Подробнее: [текст резюме](TEXT-EXTRACTION.md#resume).

«Настроить позже» возвращает в резюме без импорта. Аккаунт и профиль сохраняются на backend; после перезагрузки настройку можно продолжить со страницы браузера или через «Продолжить настройку» / «Загрузить из HH». Список кандидатов и галочки не сохраняются: после перезагрузки нужно заново запросить актуальные карточки.

## Сканирование поисков

Ожидание каждого запроса починки ограничено 210 секундами. Backend отводит всей команде
диагностики и починки 12 минут, веб ожидает её результат до 13 минут, включая запас на получение статуса.

ИИ-починка селекторов чтения выполняется в два шага через Generation Agent (для этой операции
Sol / medium). Сначала получается полный кандидат с обоснованиями, затем универсальная проверка
его CSS/XPath на инертном очищенном снимке даёт количества и примеры для независимого второго запроса.
Первый кандидат не сохраняется. Если второй ответ оставляет неподтверждённые применимые поля, страница изменилась
или финальные проверки контракта/штатного чтения не прошли, локальные селекторы не меняются.
Структурный PASS сам по себе не доказывает смысловую правильность или полноту прочитанных данных.
Поля STATE_NOT_CHECKED не подтверждаются и не изменяются: например, признаки архива не блокируют
починку заголовка и описания обычной вакансии. Их исходные значения сохраняются даже при предложении ИИ.
Кратность поля внутри `scope.anyOf` проверяется отдельно для каждой родительской области:
одна кнопка просмотра отклика в верхней панели и одна в уведомлении о доставке допустимы.
Дубликаты внутри одной области по-прежнему считаются ошибкой. Если ошибка относится к полю,
исключённому из ИИ-починки, диагностика выводит пояснение вместо кнопки исправления.
`STATE_NOT_CHECKED` («Состояние не проверено») обозначает неоткрытую форму, нераскрытый список
или другое ненаблюдаемое состояние. Такой статус не портит результат проверки текущего состояния,
но не подтверждает исправность соответствующих селекторов. `NOT_APPLICABLE` означает, что поле
не нужно в текущем варианте интерфейса, а `NOT_CHECKED` — что применимую проверку выполнить не удалось.
Для открытых форм проверяются id, связь кнопки с найденной формой (в том числе внешней), идентификаторы
вариантов резюме и допустимые значения ARIA. Неактивная кнопка отмечается отдельно; поля не заполняются.
Если архивность видна по признакам HH, но ни один архивный селектор реестра её не подтверждает,
выдаётся FAIL. Для архивной страницы доступна ИИ-починка заголовка и признаков архива;
селекторы управления откликом не изменяются.

1. Откройте браузер нужного аккаунта и войдите в HH. Добавьте ссылку поиска. Если в ней есть `resume`, нужное локальное резюме определяется по hash и поле выбора заблокировано; если параметра нет, выберите резюме в форме. Параметр автоматически не дописывается в URL.
2. Нажмите «Сканировать». Агент проверит вход и наличие резюме в профиле, затем откроет отдельную вкладку выдачи. Рабочие вкладки создаются в фоне; при ошибке нужная вкладка остаётся открытой для ручной проверки без переключения фокуса.
3. Дождитесь окончания сбора: не меняйте фильтры и не закрывайте эту вкладку. На успехе она закрывается, при ошибке остаётся для ручной проверки.

Команда `SCAN_SEARCH` получает профиль, URL, ID поиска и лимит 1–20 страниц. Выбранный пользователем `order_by` сохраняется, а `items_on_page=100` и `page=0` выставляются принудительно. Номер страницы увеличивается только при наличии следующей страницы в пагинации HH; между переходами есть пауза. Повторяющиеся ID вакансий объединяются, повтор целой страницы считается ошибкой.

После загрузки DOM сканер ждёт стабилизации карточек и пагинации до 45 секунд, проверяя снимок каждые 500 мс. После чтения каждой страницы агент отдельно сообщает backend текущую страницу, число уже собранных карточек и приблизительный `totalResults`; сбой этой служебной отправки не отменяет сбор и финальную доставку вакансий.
Быстрая страница завершается после шести одинаковых снимков подряд и не ждёт весь таймаут.

Источник списка — актуальные DOM-карточки `[data-qa="vacancy-serp__vacancy"]`. Встроенный `HH-Lux-InitialState` используется только как дополнительный структурированный снимок, когда число вакансий и вся последовательность их ID в точности совпадают с уже стабилизировавшимся DOM; устаревший или повреждённый JSON игнорируется без падения сканирования. Во время сканирования агент не открывает деталки, не читает описания, cookies или токены. В backend отправляются поля карточек и нормализованное обогащение совпавшего снимка. Зарплата карточки сохраняется текстом, числовой диапазон — только для месячных рублей с известным признаком налога. Описание читается отдельно при обработке отклика: [текст вакансии](TEXT-EXTRACTION.md#vacancy).

При капче, потере входа, изменении фильтров или нераспознанной разметке сбор завершается ошибкой без частичного сохранения. Отсутствие карточек без явного пустого состояния не считается успешным пустым поиском. Backend ждёт начала команды до 60 секунд, выполнения — до 40 минут. После обновления нужно перезапустить backend, frontend и агент вместе.

Ручная проверка итерации: создать поиск с другой сортировкой/размером страницы, проверить нормализацию; собрать 1–2 страницы; добавить вакансии/компании в избранное и вакансию в очередь; повторить сбор и убедиться, что дубли не появились, а отбор сохранён. Проверить переключение аккаунта и ошибку при закрытии рабочей вкладки.

## Требования

- Node.js 24.12+ в ветке 24.x (также поддерживается 22.x начиная с 22.18)
- npm
- установленный Google Chrome

## Команды

```powershell
npm.cmd ci
npm.cmd start
```

Команды выполняются из `browser-agent` в Windows PowerShell. Для разработки с автоматическим перезапуском используйте `npm.cmd run dev`. Установка зависимостей Windows и порядок запуска всех компонентов описаны в [infra/README.md](../infra/README.md).

По умолчанию профили хранятся в пользовательском каталоге данных приложения. Для каждого профиля из HH Clicker создаётся отдельная директория:

```text
%LOCALAPPDATA%\HH Clicker\data\browser-agent\profiles\<profileId>
```

Корневой путь можно переопределить переменной окружения `HH_CLICKER_BROWSER_PROFILE_DIR`.

Все параметры браузера и устройства предоставляет установленный Google Chrome. Browser Agent не подменяет User-Agent, Client Hints, CPU, память и прочие характеристики окружения. Если на виртуальной машине Chrome зависает при открытии окна, можно задать `HH_CLICKER_CHROME_DISABLE_GPU=true`: агент передаст Chrome флаг `--disable-gpu`. Эта настройка влияет на графический режим браузера и по умолчанию выключена. Таймаут открытия Chrome по умолчанию составляет 30 секунд; для медленной VM его можно увеличить через `HH_CLICKER_CHROME_LAUNCH_TIMEOUT_MS` (миллисекунды).

Backend по умолчанию доступен по адресу `http://localhost:8080`. Настройки подключения можно переопределить переменными окружения:

- `HH_CLICKER_BACKEND_URL`;
- `HH_CLICKER_AGENT_ID`;
- `HH_CLICKER_AGENT_VERSION`;
- `HH_CLICKER_HEARTBEAT_INTERVAL_MS`;
- `HH_CLICKER_COMMAND_POLLING_INTERVAL_MS`;
- `HH_CLICKER_REQUEST_TIMEOUT_MS`.

Остановить агент и закрыть управляемый браузер можно сочетанием `Ctrl+C`.

Для запуска собранного агента предусмотрены команды:

```powershell
npm.cmd run build
node dist/main.js
```
